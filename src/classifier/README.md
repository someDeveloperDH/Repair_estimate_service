# 신발 / 의류 분류기

수선 접수 사진을 **품목(신발·의류·가방·기타)** 과 **신발 종류 14종** 으로 분류한다.
학습 없이 동작한다.

```bash
pip install -r requirement.txt

python -m src.classifier.classify --src ./images --out ./out   # 분류 → labels.csv
python -m src.classifier.sort     --src ./images --out ./out   # 폴더 배치 + 교차검증
```

---

## 왜 zero-shot인가 (YOLO를 안 쓴 이유)

접수 사진에는 **정답 라벨이 하나도 없다.** YOLO는 detection이든 `yolo-cls`든 지도학습이라
수천 장을 먼저 라벨링해야 시작할 수 있다.

게다가 접수 사진은 품목이 화면을 거의 채우고 있어 **검출할 것이 없다.** 필요한 건
"이게 무엇인가"라는 한 줄이다. (파손 *부위* 를 찾는 단계는 별개이며 detector가 맡는다)

SigLIP2 zero-shot은 텍스트 프롬프트만으로 동작하고, 클래스를 바꿀 때
`taxonomy.py` 만 고치면 된다. 재라벨링도 재학습도 없다.

---

## 3개 축을 독립적으로 분류한다

| 축 | 클래스 |
|---|---|
| `item_type` | 신발 / 의류 / 가방 / 기타 |
| `view` | 전체샷 / 밑창 / 클로즈업 |
| `shoe_type` | 로우탑·하이탑 스니커즈 / 러닝화 / 구두 / 로퍼·슬립온 / 앵클부츠·워커 / 롱부츠 / 어그·퍼부츠 / 힐·펌프스 / 플랫슈즈 / 샌들 / 슬리퍼·슬라이드 / 등산화·트레킹화 / 스노보드·스키부츠 |

**`view` 축이 따로 있는 이유** — 실측 8,754장 중 **2,186장(25%)이 밑창샷**이었다.
밑창만 보고 러닝화인지 구두인지는 원리적으로 판별할 수 없다. 이걸 종류 축에 섞으면
전체 정확도가 오염되므로 분리했다. `sort.py`는 밑창·클로즈업을 별도 폴더로 뺀다.

## 실측 성능

### 품목 분류 (신발 / 비신발)
정답을 아는 43장(신발 10 · 가방 4 · 비신발 29)에서 **43/43 = 100%**.
장갑·가방끈·스포츠브라·헬멧이 전부 신발이 아닌 것으로 잡혔다.

### 신발 종류
8,754장 실행 결과를 k-means로 교차검증한 군집 순도:

| 신뢰 | 클래스 |
|---|---|
| **0.90~1.00** | 롱부츠 1.00 · 샌들 0.99 · 플랫 0.96 · 등산화 0.95 · 구두 0.95 · 슬리퍼 0.95 · 힐 0.93 · 스노보드 0.90 |
| **0.62~0.86** | 어그 0.86 · 앵클부츠 0.74 · 로퍼 0.62 |
| **0.25~0.46** | 하이탑 0.46 · 러닝화 0.32 · 로우탑 0.25 |

> 스니커즈 3종의 낮은 순도는 **라벨 오류가 아니다.** 육안 감사에서 라벨은 정확했다.
> k-means가 임베딩을 색·소재·촬영각도로 나누기 때문에 스니커즈가 여러 군집에 흩어진다.
> 다만 **로우탑 ↔ 러닝화 경계는 실제로 모호하다** (뉴발란스 574 같은 러닝 헤리티지).
> 이 구분이 중요하지 않은 용도라면 세 클래스를 "운동화" 하나로 합치는 편이 낫다.

### 속도
M1 Pro(MPS) `base` 모델 기준 **약 40 img/s** — 8,754장에 215초.
더 정확한 결과가 필요하면 `--model large`(so400m-384). 6~8배 느리다.

## 클래스 추가하는 법

`taxonomy.py`에 프롬프트를 넣고 다시 돌리면 끝이다.

실제 사례: 첫 실행 후 무작위 32장을 육안 감사했더니 **등산화가 러닝화로,
스노보드부츠가 앵클부츠로** 새고 있었다. 두 클래스를 추가하자 **760장이 제자리를 찾았다**
(앵클부츠 650 → 224, 스노보드 337 신규, 등산화 120 신규). 재학습은 없었다.


## 출력

```
out/
├── labels.csv        품목·뷰·종류 + 신뢰도 + margin (UTF-8 BOM, 엑셀에서 바로 열림)
├── embeddings.npy    이미지 임베딩 N×768 — 유사검색·재분류·교차검증에 쓴다
├── taxonomy.json     이 실행에 쓰인 클래스 정의 (재현성)
├── classified.csv    폴더 배치 결과
└── classified/
    ├── 01_신발/<종류>/
    ├── 02_밑창샷/          종류 판별 불가하므로 분리
    ├── 03_클로즈업/        종류 판별 불가하므로 분리
    ├── 04_의류/  05_가방/  06_기타/
    └── 09_검토필요/<추정종류>/   margin < 0.15
```

`sort.py`는 **하드링크**로 배치한다. 추가 디스크 0바이트이고, `classified/`를 통째로
지워도 원본에 영향이 없다.

## 신뢰도 읽는 법

- `*_conf` — 축 안에서의 softmax 확률
- `*_margin` — **1위와 2위의 격차.** 이쪽이 더 쓸모 있다

SigLIP은 sigmoid 기반이라 `logit_scale`(~118)에서 확률이 전부 0.999로 포화된다.
그래서 축 안에서 softmax(온도 100)를 다시 취한다. argmax는 같고 신뢰도만 살아난다.

`margin < 0.15`면 1·2위가 거의 붙은 것이므로 사람이 확인해야 한다.
실측에서 전체의 약 8%가 여기 해당했고, 대부분 로우탑 ↔ 러닝화 경계였다.
임계값은 `sort.py`의 `MARGIN_MIN`에서 조정한다.

## 알아둘 것

- 첫 실행 때 HuggingFace에서 모델을 내려받는다(base 약 1.5GB). 이후 캐시된다.
- `transformers` 5.x는 `get_*_features`가 `ModelOutput`을 반환한다.
  `model.py`의 `_tensor()`가 4.x/5.x를 모두 처리한다.
- CSV 컬럼명이 `item`이 아니라 **`item_type`** 이다.
  pandas `Series.item()` 메서드와 충돌해서 `df.apply(axis=1)` 안에서
  `row.item`이 컬럼이 아니라 메서드로 잡히는 함정이 있다.
